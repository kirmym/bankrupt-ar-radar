# План финальных доработок до работающего прототипа

Актуально на 1 сентября 2026 года. План составлен по текущей ветке `codex`,
живой базе после импорта ЦДТ и фактическому пользовательскому сценарию web/API.

## Статус выполнения плана

Все задачи, необходимые для локального рабочего прототипа, реализованы в
рабочем дереве ветки `codex`.

- **Этап 1. Лента:** list/detail API используют единый fail-closed gate;
  `deadline_before` и сортировка работают по `Trade.applications_to`; в DTO и
  web отображаются статус торгов, срок подачи заявки, ценовой интервал и
  источник. Добавлены представления `active`, `review` и `ready`.
- **Этап 2. Review-очередь:** строгие рекомендации A/B не ослаблены; добавлены
  API, dashboard-счётчики и Telegram-команда `/review` для кандидатов с
  положительным предварительным EV и явными gaps.
- **Этап 3. Документы:** добавлены кэш по `(source_host, external_id)`, повторное
  использование текста и хеша, tri-state юридические факты, фрагменты evidence,
  запрет применения критического предложения без evidence, асинхронные OCR,
  ограничение batch/таймаутов и приоритет ближайшего срока заявки.
- **Этап 4. Запуск:** добавлены `scripts/prototype.ps1`, команды
  `ar-radar files` и `ar-radar prototype-run`, новые operational stats,
  настройки в `.env.example`, dashboard и README.

### Фактическая проверка

- Backend: `ruff check`, `mypy` и **192 теста** — успешно.
- Web: lint, **2 теста** и production build — успешно.
- Bot: Ruff и mypy — успешно; тесты бота — успешно.
- PowerShell: `scripts/prototype.ps1` проходит синтаксический разбор.
- Live Docker smoke на изолированном compose-проекте: импорт ЦДТ завершён,
  получено 283 активных лота с будущим сроком заявки, 2 кандидата в review,
  0 строгих A/B-рекомендаций и 0 лотов со статусом `in_progress`.
- Повторная обработка документов переиспользовала 19 из 20 файлов через кэш;
  повторный цикл не скачивал их заново.

После успешного live smoke Docker Desktop остановил Linux engine. Поэтому после
последней пересборки образа не удалось повторно выполнить команды внутри
контейнера (`alembic check` и `ar-radar --help`); это инфраструктурный блокер,
а не ошибка приложения. Сборка образа до остановки engine завершилась успешно,
а все доступные локальные проверки пройдены. В первом bounded batch часть
документов остаётся в очереди (`pending`/`needs_review`) по проектному дизайну:
очередь обрабатывается ограниченными циклами и не блокирует выдачу review.

## 1. Цель ближайшего релиза

Ближайший результат следует назвать **рабочим прототипом**, а не полноценной
системой due diligence. Он должен помогать аналитику ежедневно получать из
реального источника список лотов дебиторской задолженности, в которых ещё можно
подать заявку, открывать исходную карточку и документы, видеть предварительную
экономику и понимать, какие проверки ещё не выполнены.

Для этого релиза допустим один стабильный источник лотов — публичный JSON ЦДТ.
Второй источник, полностью автоматические КАД/ФССП и юридическое заключение по
документам не должны задерживать первый полезный результат.

Прототип считается работающим, если оператор может выполнить цикл:

1. Запустить проект одной командой в Docker.
2. Дождаться успешного импорта и увидеть время последнего снимка.
3. Открыть ленту доступных для участия лотов.
4. Увидеть статус торгов, источник и **срок подачи заявки**, а отдельно — конец
   текущего ценового интервала.
5. Получить хотя бы очередь кандидатов на ручную проверку, даже если строгих
   рекомендаций класса A/B ещё нет.
6. Открыть карточку кандидата, исходную публикацию и документы, увидеть цену,
   EV, стоп-факторы и явно отмеченные пробелы данных.
7. Повторный запуск не создаёт дубликаты и не возвращает в выдачу торги, по
   которым участие уже невозможно.

Прототип **не** должен автоматически подавать заявку, обещать взыскание,
называть непроверенный факт достоверным или скрывать отсутствие данных.

## 2. Подтверждённое текущее состояние

### Что уже работает

- Публичный источник ЦДТ импортируется без платного API.
- Последние live-запуски завершились успешно; последний снимок содержит 284
  карточки.
- Единый gate исключает начавшиеся, завершённые, отменённые, просроченные и
  неизвестные торги из API, скоринга и алертов.
- В живой базе 284 лота дебиторской задолженности имеют будущий срок подачи
  заявки; у 235 распознан текущий ценовой интервал.
- Для 154 активных лотов найден дебитор.
- API, web-карточка, история скоринга, источники, typed gaps, feedback и
  Telegram outbox уже реализованы.
- Docker-образ включает Tesseract и Poppler; OCR сканированных PDF работает.
- Миграции доведены до `0012`; CI проверяет `alembic upgrade head` и
  соответствие ORM миграциям.
- В последнем контрольном прогоне проходят 192 backend-теста, Ruff, mypy,
  2 web-теста и production-сборка web.

### Что мешает получить полезный результат сейчас

| Приоритет | Проблема | Фактическое проявление |
|---|---|---|
| P0 | В ленте смешаны два разных дедлайна | Фильтр и сортировка `deadline` используют конец ценового интервала, хотя UI называет его дедлайном подачи заявки. В list DTO нет статуса торгов, `applications_to` и источника. |

| P1 | Недостаточно операционной видимости | `/workers/status` показывает циклы, но UI не показывает очередь документов, причины исключения лотов, состояние источника и причину пустой выдачи. |
| P1 | Остановка контейнера может быть долгой | OCR выполняется синхронно внутри файлового цикла; при остановке активного процесса контейнер ранее завершался принудительно. Нужны bounded batch/timeouts и проверка graceful shutdown. |

В текущем live-снимке уже есть **3 кандидата для ручной проверки**: у них
положительный предварительный EV, распознанная цена, нет стоп-факторов и есть
будущий срок заявки. Они не являются рекомендациями, поскольку для каждого не
завершены проверки ФССП, КАД, статуса дебитора и документов. Значит, быстрый
полезный прототип можно получить без ослабления строгого A/B-алерта: требуется
отдельная честно обозначенная очередь `Нужна проверка`.

## 3. Финальный план реализации

### Этап 0. Зафиксировать текущую базу — 0,5 дня

1. Проверить, что в diff нет секретов, локальных дампов и артефактов OCR.
2. Сохранить текущие изменения отдельным коммитом после полного прогона тестов.
3. На пустой PostgreSQL применить миграции `base -> head`, затем выполнить
   `alembic check`.
4. Зафиксировать один обезличенный raw snapshot ЦДТ как интеграционную fixture,
   чтобы gate и пользовательская выдача проверялись независимо от состояния
   внешнего сайта.
5. Telegram-токен, ранее переданный через чат, перед развёртыванием отозвать и
   выпустить заново. В репозитории хранить только имя переменной окружения.

**Приёмка:** `git status` чистый; секретов в Git нет; пустая база мигрирует до
одной головы; backend/web/бот и Docker build проходят из зафиксированного commit.

### Этап 1. Исправить семантику рабочей ленты — 0,5–1 день

1. Добавить в list response компактные поля торгов:
   `trade_status`, `applications_from`, `applications_to`, `source_name`,
   `source_url`, `participation_exclusion_reason`.
2. Исправить `deadline_before` и сортировку `deadline`: они должны работать по
   `Trade.applications_to`, а не по `Lot.current_interval_to`.
3. В web показывать два разных времени:
   - «Заявку можно подать до» — `applications_to`;
   - «Текущий ценовой интервал до» — `current_interval_to`.
4. Разделить ленту на понятные представления:
   - `Можно участвовать` — единый fail-closed gate;
   - `Предстоящие` — объявленные лоты, для которых ценовой интервал ещё не
     начался;
   - `Нужна проверка` — кандидаты с gaps, но без подтверждённых стоп-факторов.
5. Не скрывать будущие лоты постоянным frontend-фильтром
   `price_status=parsed`; состояние цены должно быть видимым фильтром или
   отдельной вкладкой.
6. Обновить dashboard: источник ЦДТ, фактическая команда запуска, время
   последнего успешного импорта, число активных/исключённых лотов.
7. Добавить интеграционные тесты list/detail API на одинаковый gate, правильный
   дедлайн и снятие лота с выдачи после смены статуса.

**Приёмка:** пользователь из строки списка видит, до какого момента принимается
заявка и откуда получен лот; сортировка ближайших дедлайнов проверяется тестом;
`in_progress`, истёкший `applications_open` и неизвестный статус отсутствуют во
всех пользовательских представлениях.

### Этап 2. Добавить безопасную очередь ручной проверки — 0,5 дня

1. Не менять строгие правила рекомендаций A/B и существующего alert worker.
2. Ввести отдельный серверный режим `review` со следующим минимальным gate:
   - участие ещё доступно;
   - текущая цена распознана и свежая;
   - предварительный EV положительный;
   - подтверждённых стоп-факторов нет;
   - gaps разрешены и обязательно показаны пользователю.
3. Сортировать очередь сначала по близости срока заявки, затем по полноте данных
   и предварительному EV. Не смешивать её с рекомендациями A/B.
4. Добавить на dashboard счётчики `Готовые рекомендации` и
   `Кандидаты на проверку` с пояснением причин, если один из счётчиков равен 0.
5. Для Telegram добавить отдельную команду `/review` или опциональный суточный
   digest. В тексте использовать формулировку «кандидат на проверку», выводить
   gaps и ссылку на источник. Автоматический срочный алерт оставить только для
   A/B без gaps.
6. Запретить отправку review-digest, если цена устарела, срок заявки истёк или
   появился стоп-фактор.

**Приёмка:** на контрольном live-снимке очередь возвращает текущие 3 кандидата;
строгая очередь A/B остаётся пустой и честно объясняет причину; ни один кандидат
с начавшимися торгами не попадает в web или Telegram.

### Этап 3. Сделать документы быстрыми и безопасными — 1–1,5 дня

1. Сохранить связь `Document -> Lot`, но кэшировать содержимое по паре
   `(source_host, external_id)`. Перед скачиванием искать уже обработанный
   экземпляр того же файла.
2. Для повторного файла переиспользовать `sha256`, текст и общие извлечённые
   факты без нового HTTP-запроса/OCR; proposal пересчитывать для конкретного
   требования, чтобы не копировать конфликтное решение из другого лота.
3. Не интерпретировать отсутствие ключевой фразы как `false`:
   - положительное совпадение -> `true` + фрагмент доказательства;
   - явная отрицательная формулировка -> `false` + фрагмент;
   - фраза не найдена или контекст неоднозначен -> `null/unknown`.
4. Для каждого предложенного критического факта сохранять хотя бы
   `document_id`, метод (`text`, `ocr`, `llm`), фрагмент текста и номер страницы,
   если его можно определить. Без evidence критический факт нельзя применять.
5. Приоритизировать документы активных лотов с ближайшим сроком заявки. Общие
   формы/шаблоны обрабатывать один раз, а не раньше уникальных доказательств.
6. Добавить счётчики `unique files`, `reused`, `pending`, `retrying`,
   `needs_review`, `completed` и возраст старейшего задания.
7. Ограничить OCR числом страниц, размером файла, временем одного задания и
   общим временем batch; отмена scheduler должна завершать контейнер без
   принудительного убийства.

**Приёмка:** два внешних CDT-файла скачиваются и распознаются не более одного
раза каждый; 198 связей лотов получают итог через кэш без 198 OCR-запусков;
отсутствующая фраза не создаёт `false`; применение факта без evidence отклоняется;
повторный files-cycle почти сразу сообщает 0 новой работы.

### Этап 4. Добавить один воспроизводимый запуск — 0,5–1 день

1. Добавить Windows-совместимый `scripts/prototype.ps1` и эквивалентную CLI-команду
   `ar-radar prototype-run`.
2. Сценарий должен:
   - проверить Docker и обязательные переменные;
   - поднять PostgreSQL и app;
   - дождаться `/ready`;
   - дождаться завершения первого ingest;
   - запустить/дождаться files, enrich и score без параллельных дублей;
   - вывести активные лоты, кандидатов review, A/B, gaps и очередь документов;
   - сохранить JSON-отчёт контрольного прогона в папку проекта.
3. Telegram и OpenAI сделать необязательными. Их отсутствие не должно ломать
   web-прототип; статус должен быть `disabled`, а не `failed`.
4. Добавить endpoint агрегированного состояния прототипа или расширить stats:
   последний успешный источник, возраст данных, очередь документов, число
   review-кандидатов и причины исключения.
5. Исправить `.env.example` и README: минимальные настройки для CDT, запуск,
   адрес web, проверка результата и безопасная настройка нового Telegram-токена.

**Приёмка:** на чистом компьютере с Docker оператор следует одному разделу
README и получает web-ленту без ручного запуска пяти модулей; команда завершается
понятным PASS/FAIL и не печатает секреты.

### Этап 5. Контрольный релизный прогон — 0,5 дня

Прогон выполняется с новой базой и новым volume:

1. Собрать образ без build cache и применить миграции.
2. Запустить полный импорт ЦДТ.
3. Дождаться одного полного цикла документов, enrichment и scoring.
4. Проверить `/health`, `/ready`, `/workers/status`, stats, list и detail API.
5. Проверить fixture-гейты и live-гейты: начавшиеся/просроченные торги отсутствуют.
6. Открыть web и вручную пройти три карточки review-кандидатов.
7. Если настроен новый Telegram-токен, отправить один тестовый review-digest в
   разрешённый chat и проверить дедупликацию повторного цикла.
8. Остановить и снова поднять стек; убедиться, что данные сохранены, миграции
   идемпотентны, а незавершённое задание продолжено безопасно.
9. Сохранить отчёт с десятью верхними результатами или всеми результатами, если
   их меньше десяти. Для каждого указать источник, срок заявки, цену, класс,
   предварительный EV, стоп-факторы и gaps.

**Финальный gate прототипа:**

- источник вернул хотя бы один актуальный лот либо система явно зафиксировала
  подтверждённый `zero-lot/source-failed` статус;
- на контрольной fixture есть минимум один review-кандидат;
- в live-потоке показываются все фактически найденные review-кандидаты;
- пользователь видит правильный срок подачи заявки и исходную ссылку;
- A/B с gaps не выдаются как готовая рекомендация;
- повторный прогон не создаёт лоты, документы или Telegram-события повторно;
- тесты, типизация, lint, web build, миграции и Docker smoke проходят;
- критических ошибок в логах нет, остановка контейнера штатная.

## 4. Что не блокирует рабочий прототип

Эти задачи важны для полноценного MVP, но должны выполняться после появления
ежедневно полезной ленты:

1. Второй независимый источник лотов: ГИС Торги, Альфалот или Lot-online.
2. Полностью автоматические проверки КАД и ФССП через CloakBrowser на устойчивом
   российском маршруте.
3. ГИР БО и расширенная финансовая модель дебитора.
4. LLM-извлечение всех юридических реквизитов и автоматическое применение
   предложений.
5. Калибровка A/B по фактическим покупкам и взысканиям.
6. Production-развёртывание, резервное копирование и многопользовательские роли.

Пока эти проверки не подключены, review-кандидаты остаются материалом для ручной
проверки, а не сигналом «покупать».

## 6. Порядок после прототипа

1. Наблюдать ЦДТ 3–7 дней: полнота, изменение статусов, пропуски, задержка.
2. Подключить второй источник и дедупликацию одного лота между источниками.
3. Настроить российский CloakBrowser-маршрут для КАД/ФССП и закрыть основные
   gaps у review-кандидатов.
4. Только после появления проверенных данных пересматривать пороги A/B и
   включать автоматические срочные Telegram-алерты.
5. Назвать релиз полноценным MVP после стабильной недельной работы, а не после
   одного успешного запуска.
