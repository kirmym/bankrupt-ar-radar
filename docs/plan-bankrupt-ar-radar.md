# План: радар прибыльной дебиторки на публичном предложении

Приложение собирает лоты **публичного предложения** на торгах по банкротству в РФ, оставляет только **права требования / дебиторскую задолженность**, обогащает карточку дебитора из открытых реестров и ранжирует лоты по ожидаемой прибыли.

Доменные критерии оценки (что считать ликвидным долгом, стоп-факторы, формула EV) — в [`likvidnaya-debitorskaya-zadolzhennost.md`](likvidnaya-debitorskaya-zadolzhennost.md). Этот файл — продуктовый и инженерный план плюс **словарь данных**: откуда брать поле и в какой реквизит модели его класть.

Материал справочный, не юридическая консультация и не гарантия прибыли.

## 2. Что система считает прибыльным

Не дисконт к номиналу («лот за 1%»), а ожидаемый денежный результат:

```text
EV = номинал × доля_взыскания × P(успех)
     − цена_текущего_интервала
     − расходы_взыскания
     − стоимость_времени
```

Лот перспективен, если одновременно:

1. требование юридически не мёртвое (давность, ИЛ, документы, не личное требование);
2. у **дебитора** (кто должен), а не у банкрота-продавца, есть источник денег;
3. `EV > 0` с запасом и класс лота **A или B** (C — только ручной watchlist).

Цена на публичке меняется по графику. Скоринг пересчитывается на каждом интервале. Алерт — когда EV стал положительным или до конца интервала осталось N часов.

## 3. Архитектура

```text
ЕФРСБ / ЭТП / файлы лота
        ↓
 нормализация лота  →  извлечение дебитора (ИНН)
        ↓
 ЕГРЮЛ, ГИР БО, КАД, ФССП, ЕФРСБ по дебитору
        ↓
 скоринг EV  →  PostgreSQL  →  веб + Telegram
```

Слои в коде:

- `connectors/` — адаптер на источник: `fetch → parse → canonical DTO`;
- `workers/` — очереди ingest / enrich / файлы / LLM / пересчёт интервала / рассылка;
- `scoring/` — чистые функции без HTTP;
- `api/` — FastAPI;
- `web/` — лента и карточка;
- `bot/` — Telegram.

Главный продуктовый риск: в карточке ЕФРСБ есть **банкрот** и цена, а **ИНН дебитора** часто только в тексте описания или в PDF на ЭТП. Без дебитора лот не попадает в «покупать», только в очередь «нужен ручной ИНН».

## 4. Роли сторон — не путать

На одном лоте минимум две разных организации. Путать их — ломать скоринг.

| Роль в модели | Кто это | Откуда обычно берётся | Для чего |
|---|---|---|---|
| **Банкрот** (`Party.role = bankrupt`) | Должник в деле о банкротстве, продавец права | Карточка торгов ЕФРСБ / ЭТП | Ссылка на дело, АУ, не источник взыскания |
| **Дебитор** (`Party.role = debtor`) | Кто должен деньги по уступаемому требованию | Текст лота, PDF, акты, решения | Главный объект due diligence |
| **Поручитель / залогодатель** | Обеспечение долга | Договор обеспечения, текст лота | Альтернативный источник денег |
| **КДЛ** | Директор / бенефициар дебитора | ЕГРЮЛ + суды о субсидиарке | Сценарий C, не MVP-покупка |
| **АУ / организатор / ЭТП** | Процедура торгов | Карточка торгов | Контакты, ссылка, задаток |

Отдельный тип лота, который **не смешивать** с дебиторкой банкрота: продажа **требования кредитора к самому банкроту** (место в реестре). Поле `Claim.kind = registry_claim_on_bankrupt`. Такие лоты в радаре ДЗ либо скрывать, либо помечать «другой бизнес».

## 6. Источники данных: куда что класть

Политика: официальный канал, если есть; HTML — fallback **в том же адаптере**. Капча = источник деградировал, радар жив.

### 6.1. ЕФРСБ — главный вход по лотам

**Зачем:** поток публички, идентификаторы, банкрот, АУ, ЭТП, описание лота, стартовая цена, задаток, классификатор, вложения сообщений.

**Где:**

- Сайт поиска: [legacy TradeList.aspx](https://old.bankrot.fedresurs.ru/TradeList.aspx) → раздел «Торги» (современный маршрут `/publications/public/offer` в текущем прогоне отдаёт страницу 404).
- Фильтры парсера: вид торгов = **Публичное предложение** (не закрытое, если не решим иначе); статус = объявлены / идут / приём заявок.
- Классификация имущества: коды из справочника `GetClassifier` (спецификация ЭТП↔ЕФРСБ v2.45). Нужны коды/подписи про **права требования, дебиторскую задолженность, имущественные права**. Точный семизначный код не хардкодить — подтянуть справочник и фильтровать по названию + белый список кодов после спайка.
- Дополнительно полнотекст: «дебиторск», «права требования», «цесси», «реституц», «субсидиар».
- Платный REST (тот же DTO на будущее): `https://bank-publications-prod.fedresurs.ru`, методы `v1/auth`, `v1/messages`, `v1/messages/{guid}`, `v1/trade-messages`, `v1/bankrupts`, `v1/trade-places`. Демо: `bank-publications-demo.fedresurs.ru`. Нужен договор с оператором.

**Сообщения, которые качать не только «объявление»:** объявление о торгах, изменение объявления, сведения о ходе (для публички цена/статистика может обновляться), результаты, отмена, приостановление.

| Поле источника (ЕФРСБ / XML ЭТП) | Реквизит модели |
|---|---|
| GUID торгов / сообщения | `Trade.efrsb_trade_guid`, `Trade.efrsb_message_guid` |
| Вид торгов = публичное предложение | `Trade.trade_kind = public_offer` (иначе отсев) |
| Форма предложения цены | `Trade.trade_form` |
| Признак повторных торгов | `Trade.is_repeat` |
| Статус торгов / лота | `Trade.status` |
| ИНН и имя ЭТП, URL площадки | `Trade.etp_inn`, `etp_name`, `etp_url` |
| ИНН/ОГРН/имя организатора | `Trade.organizer_*` |
| ИНН и ФИО АУ | `Trade.am_*` |
| ИНН/ОГРН/имя **банкрота** | `Party(role=bankrupt)` |
| Номер дела, суд | `Trade.case_number`, `court_name` |
| `Application.TimeBegin` / `TimeEnd` | `Trade.applications_from` / `applications_to` |
| `PaymentInfo` | `Trade.payment_info` |
| `SaleAgreement` | `Trade.sale_agreement_rules` |
| `Lot.LotNumber` | `Lot.lot_no` |
| `Lot.StartPrice` | `Lot.start_price` |
| `Lot.Advance` / `AdvancePercent` | `Lot.deposit_amount` / `deposit_percent` |
| `Lot.TradeObjectHtml` | `Lot.description_html` → `description_text` |
| `Lot.PriceReduction` | `Lot.price_reduction_html` → `PriceInterval[]` |
| `Lot.Classification.IDClass` | `Lot.classifier_codes[]` |
| Вложения сообщения / `Attach` | `Document` |
| Ссылка на карточку | `Trade.efrsb_url` |

**Чего в ЕФРСБ обычно нет (не ждать как структурированное поле):** ИНН дебитора, тело vs пени, обеспечение, срок давности, ИЛ, платёжеспособность дебитора.

Периодичность MVP: опрос каждые **15–30 минут**. Сырой снимок хранить.

### 6.2. ЭТП — актуальная цена, файлы, дедлайн шага

**Зачем:** текущая цена интервала часто точнее, чем HTML `PriceReduction` в ЕФРСБ; документы лота часто только на площадке.

**Где (MVP — 2–3 площадки по факту доли ДЗ после спайка, ориентир):**

- ЦДТ / [elektortorgi.ru](https://www.elektortorgi.ru)
- Сбербанк-АСТ (банкротный контур)
- Фабрикант

Остальные ЭТП в MVP: только `Trade.etp_url`, без парсера файлов.

Ссылка на торги берётся из карточки ЕФРСБ, не угадывается.

| Поле на ЭТП | Реквизит модели |
|---|---|
| Номер торгов, номер лота | сверка с `trade_id_on_etp`, `lot_no` |
| Цена текущего периода публички | `Lot.current_price` |
| Дата/время окончания текущего периода | `Lot.current_interval_to` |
| Таблица периодов снижения | `PriceInterval[]` (перекрывает разбор ЕФРСБ, если полнее) |
| Цена отсечения | `Lot.cutoff_price` |
| Список файлов лота | `Document.url`, `Document.kind` |
| Статус лота (снят, есть заявка) | `Trade.status` / служебные флаги |
| Реквизиты задатка, если подробнее | `Trade.payment_info` |

Этап 2: скачать PDF/сканы → текст → LLM-факты в `Claim` и `Party(debtor)`.

Разные ЭТП = разные HTML. Каждый адаптер изолирован. Не парсить личные кабинеты и не обходить ЭЦП.

### 6.3. Текст лота и файлы — дебитор и юридические факты

**Зачем:** единственный массовый способ узнать, **кто должен**.

| Что извлекаем | Откуда | Реквизит |
|---|---|---|
| ИНН дебитора (10/12 цифр рядом с «должник», «дебитор», «к ООО») | `description_text`, PDF | `Party(role=debtor).inn` |
| ОГРН, наименование дебитора | то же | `ogrn`, `name` |
| Номинал («задолженность 12 345 678 руб.») | то же | `Claim.principal`, при отсутствии — `Lot.nominal_claimed` |
| Вид требования | ключевые слова: поставка / заём / реституция / субсидиарка / реестр | `Claim.kind` |
| Номер арбитражного дела о взыскании | «А40-12345/2023» | `Claim.court_case_no`, `has_judgment` |
| ИЛ, ФССП | «исполнительный лист», «производство №» | `has_writ`, `enforcement_alive` |
| Даты договора и просрочки | договор, акты | `base_date`, `due_date` → оценка `limitations_deadline` |
| Обеспечение | «залог», «поручитель», «банковская гарантия» | `Claim.secured`, `guarantor` |
| Запрет уступки | «без согласия должника не уступается» | `assignment_forbidden` |
| Корзина | много ИНН / «перечень дебиторов» без сумм | `Lot.bundle_flag` |

Правила извлечения (regex + словарь) в MVP. LLM — этап 2, только заполняет JSON-схему фактов, не ставит класс лота.

Если ИНН не извлечён: `gaps += debtor_inn_missing`, класс не выше ручной очереди.

### 6.4. ЕГРЮЛ / ЕГРИП — статус дебитора

**Зачем:** стоп-факторы ликвидации, недостоверности, «однодневки».

**Где:**

- Поиск: [egrul.nalog.ru](https://egrul.nalog.ru) по ИНН.
- Карточка / PDF-выписка (открытые сведения).
- Сервис ФНС «Прозрачный бизнес»: [pb.nalog.ru](https://pb.nalog.ru).
- Опционально платная интеграция выгрузок ЕГРЮЛ (абонентский доступ ФНС).

Ключ запроса: `Party.inn` дебитора (и отдельно банкрота — только для справки, не для EV).

| Сведение ФНС | Реквизит `Party` |
|---|---|
| Наименование, ИНН, ОГРН | `name`, `inn`, `ogrn` |
| Состояние: действующее / в процессе ликвидации / исключено | `status` |
| Дата регистрации | `reg_date` |
| Юр. адрес | `address` |
| ЕИО (директор) | `director_name` |
| Отметки о недостоверности адреса / ЕИО / учредителей | `invalid_address`, `invalid_director` |
| Решение о предстоящем исключении | `pending_exclusion` |
| Дата прекращения / способ | `status` + дата в снимке |

Кэш 12–24 часа. Стоп-фактор: исключено / ликвидация без поручителя и без КДЛ с активами.

### 6.5. ГИР БО — масштаб дебитора

**Зачем:** `долг / выручка`, `долг / ЧА`, `долг / деньги`.

**Где:** [bo.nalog.ru](https://bo.nalog.ru) поиск по ИНН. Официальный REST ФНС для массовой выгрузки — платный (ориентир рынка — сотни тысяч ₽/год). В MVP — карточка организации, best-effort.

Брать **последний доступный год**. Малый бизнес на упрощёнке может не отдавать полный баланс — тогда пробел `bo_missing`, скоринг без финкоэффициентов, стоп-факторы ЕГРЮЛ/ФССП всё равно работают.

| Показатель БО (код строки) | Реквизит `Party` | Куда в скоринг |
|---|---|---|
| 2110 Выручка | `revenue` | долг / (revenue/12) |
| 1250 Денежные средства | `cash` | долг / cash |
| 1200 Оборотные активы | `current_assets` | запас ликвидности |
| 1230 ДЗ самого дебитора | (опционально отдельное поле) | качество его баланса |
| 1300 Капитал и резервы | `equity` | долг / ЧА |
| 1510 + 1520 (+ 1550 по необходимости) | `short_term_liab` | доля вашего долга в его КЗ |
| 2400 Чистая прибыль (или 2300) | `profit` | убыточность |
| Год отчёта | `bo_year` | свежесть |

Строка 1230 **дебитора** — это его дебиторка, не наш лот. Не подставлять в `Claim.principal`.

### 6.6. Картотека арбитражных дел

**Зачем:** банкротство дебитора, поток исков о взыскании, уже выигранное дело по **этому** долгу.

**Где:** [kad.arbitr.ru](https://kad.arbitr.ru) по ИНН / наименованию / номеру дела. Официального API нет. Кэш сильный, RPS низкий. Casebook — поздняя платная замена адаптера.

| Наблюдение | Реквизит |
|---|---|
| Дело о банкротстве дебитора на ходу | `Party.kad_bankruptcy_open` |
| Число дел, где дебитор ответчик | `kad_as_defendant_count` |
| Номер дела совпал с `Claim.court_case_no` | `Claim.has_judgment` (уточнять статусом) |
| Определение о правопреемстве / ИЛ в текстах актов | `has_writ` (этап 2, по тексту) |

Дело банкротства **продавца** (банкрота по лоту) не класть в `kad_bankruptcy_open` дебитора.

### 6.7. ФССП

**Зачем:** уже взыскивают, пустой должник, сумма чужих ИП.

**Где:** предпочтительно официальный API [api-ip.fssprus.ru](https://api-ip.fssprus.ru) (токен). Запасной контур — банк данных на [fssp.gov.ru](https://fssp.gov.ru). Запрос: ИНН / наименование / ФИО+регион для ИП и физлиц.

| Сведение | Реквизит |
|---|---|
| Сумма открытых ИП | `Party.fssp_sum` |
| Предмет «кредит», «задолженность» | для справки в карточке |
| Окончание по п. 4 ч. 1 ст. 46 (нет имущества) | `fssp_uncollectible` |
| Совпадение реквизитов ИЛ с нашим требованием | `Claim.enforcement_alive` |

Сравнение: `fssp_sum` vs `Claim.principal` — если чужие ИП >> нашего долга и имущества нет, источник денег слабый.

### 6.8. ЕФРСБ по дебитору (не по лоту)

**Зачем:** сам дебитор уже в банкротстве — тогда это не «живой контрагент», а ставка на конкурсную массу / субсидиарку.

**Где:** поиск должника на bankrot.fedresurs.ru / `v1/bankrupts` по ИНН.

| Сведение | Реквизит |
|---|---|
| Найдена карточка должника, процедура не завершена | `Party.status = bankruptcy`, `kad_bankruptcy_open` |
| Конкурс завершён, исключён | стоп-фактор, если нет КДЛ |
| Сообщения о субсидиарке / убытках с КДЛ | этап 2, отдельный `Claim.kind = subsidiary` |

### 6.9. Прозрачный бизнес и прочее (best-effort)

| Источник | URL | Куда |
|---|---|---|
| Прозрачный бизнес | [pb.nalog.ru](https://pb.nalog.ru) | `tax_debt`, `headcount`, спецрежим |
| Федресурс залоги / лизинг | [fedresurs.ru](https://fedresurs.ru) | обеспечение, залоги дебитора (этап 2) |
| Росреестр / ГИБДД | не MVP | имущество физлица-КДЛ |
| СПАРК / Контур / Casebook | платно, не MVP | замена пачки коннекторов |

## 7. Извлечение дебитора из текста

Порядок:

1. Все ИНН из `description_text` и имён файлов.
2. Вычесть ИНН банкрота, организатора, АУ, ЭТП.
3. ИНН в контексте «дебитор / должник / задолженность / к ООО / к ИП» — кандидат №1.
4. Если один оставшийся ИНН юрлица — принять с `confidence = medium`.
5. Если 0 — `debtor_inn_missing`.
6. Если много — `bundle_flag`, не склеивать в одного дебитора; в MVP такой лот не в «покупать».

Валидация ИНН: контрольные суммы 10/12 знаков. Потом обязательный запрос ЕГРЮЛ: имя из выписки должно быть похоже на имя в тексте лота (иначе ложный ИНН).

Метрика спайка этапа 0: доля лотов с верно извлечённым ИНН дебитора без файлов ЭТП. Если &lt; 30% — в MVP обязателен хотя бы один ЭТП-адаптер с файлами.

## 8. Скоринг: какие реквизиты на вход

Формула EV использует:

| Вход | Реквизит |
|---|---|
| Номинал | `Claim.principal` или `Lot.nominal_claimed` или, хуже, `Lot.start_price` |
| Цена покупки сейчас | `Lot.current_price` |
| Доля взыскания и P(успех) | таблица класса A–D по стоп-факторам и масштабу |
| Расходы | константы сценария: мировое / суд / банкротство дебитора |
| Время | 0.5 / 1.5 / 3 года × ставка альтернативы |

Жёсткий отсев (класс D, алерт «покупать» запрещён) — по реквизитам:

- нет `debtor.inn`;
- `status` ∈ {исключено, ликвидация} без поручителя/КДЛ;
- банкротство дебитора завершено без выплат;
- `limitations_deadline` или `il_present_deadline` в прошлом;
- `personal_claim` или неденежное требование;
- `bundle_flag` без расшифровки;
- нет источника: пустые `revenue`/`equity`/`cash` **и** `fssp_uncollectible` **и** нет `secured`.

Класс A/B (сигналы): `has_judgment` + `has_writ` + живое ИП; `kind = restitution` и дебитор ИП/ФЛ; действующий ЕГРЮЛ; `secured`; долг &lt; 1 месяца выручки.

Выход в `ScoreSnapshot`: класс, EV-коридор, `max_bid` (в MVP ≈ текущая цена vs EV), `scenario`, `stop_factors[]`, `gaps[]`.

LLM не пишет `class` и не пишет `max_bid`.

## 9. Интерфейсы MVP

Веб:

- лента только публичка + `is_receivable`;
- сортировка: EV, класс, `current_interval_to`;
- фильтры: класс, цена, ЭТП, «дебитор извлечён», «есть суд»;
- карточка: сырой текст, дебитор, график цены, снимки реестров, скоринг, ссылки ЕФРСБ / ЭТП / КАД;
- ручной ИНН дебитора → пересчёт enrich+score;
- кнопки «в работу / отказ / куплено» → `UserFeedback`.

Telegram:

- срочный алерт: класс A/B и EV &gt; 0 на текущем интервале, либо до `current_interval_to` &lt; 4 часов;
- утренний дайджест топ-N;
- в сообщении: цена, EV, класс, ИНН дебитора, дедлайн, ссылки.

## 10. Этапы поставки

### Этап 0. Спайк

Каркас `bankrupt-ar-radar/` (Docker: один API-контейнер с asyncio-воркерами + PostgreSQL; Redis/ARQ не используются). Снять ~50 живых лотов публички-ДЗ с ЕФРСБ. Померить извлечение ИНН. Go/no-go по ЭТП-файлам.

### Этап 1. MVP-радар

Ingest ЕФРСБ 15–30 мин. Классификатор ДЗ. Скоринг v1. Веб + Telegram. Enrich: ЕГРЮЛ + ФССП + ЕФРСБ-дебитор. КАД и ГИР БО — best-effort. Ручной ИНН.

Готово, когда за неделю живого потока человек согласен, что A/B «смотреть стоит», а Telegram не забит мусором.

**Текущий срез реализации:** ingest ЕФРСБ работает через legacy `TradeList.aspx`/`TradeCard.aspx` с typed-ошибками разметки и CloakBrowser fallback; EГРЮЛ/ФССП/КАД соблюдают политику «API только явно разрешённых бесплатных провайдеров, иначе HTML-парсер»; API защищает production-данные ключом; Telegram-бот закрыт по умолчанию; дедупликация алертов стабильна; локальные bootstrap/smoke-скрипты добавлены.

### Этап 2. Due diligence

2–3 ЭТП, файлы, PDF/OCR, LLM→JSON фактов, скоринг v2, макс. ставка, сценарии, шаблон письма АУ (копирование, не автоотправка).

### Этап 3. Калибровка

Фидбек взысканий. Подмена парсера ЕФРСБ на REST при договоре. Алерт «0 лотов за 6 часов». Без автоставки.

### Этап 4. Интерфейс аналитика и доставка сигналов

Серверные фильтры и сортировка с URL-состоянием, полное досье лота с документами
и историей скоринга, feedback с исходом взыскания, а также Telegram outbox с
получателем, событием, версией интервала, retry и дедупликацией. Непроверенные
данные показываются как gaps/data state; локальные ссылки и персональные данные
не отправляются во внешние сообщения.

### Этап 5. Gate публичных предложений по доступности участия

Импорт и выдача в API ограничиваются только предложениями, по которым участие
ещё возможно: `announced` (объявлены торги), `applications_open` (идёт приём
заявок) и `in_progress` (торги идут). Завершённые, отменённые, не состоявшиеся,
приостановленные, находящиеся на подведении итогов и предложения с неизвестным
статусом отбрасываются; фильтр применяется при нормализации источников, ingest
и в SQL-запросе API.

Порядок в коде: каркас → ЕФРСБ + ИНН → скоринг v1 → веб → Telegram → ЕГРЮЛ/ФССП → этап 2.

Правила домена кодировать из [`likvidnaya-debitorskaya-zadolzhennost.md`](likvidnaya-debitorskaya-zadolzhennost.md), не выдумывать заново.

## 11. Ограничения парсеров

При `401/403/429`, сетевой ошибке или challenge основной HTTP-транспорт повторяет загрузку через уже запущенный профиль CloakBrowser по CDP. 4xx/5xx и тело страницы 404 сохраняются как typed-ошибки доступа, а не как «пустой» результат. Капча проходит вручную, автоматического обхода нет.


- Падение КАД не останавливает ingest лотов.
- Идемпотентность лота, хранение сырых снимков.
- Секреты (ФССП, Telegram, LLM) только в `.env`.
- Персональные данные директоров — только для скоринга.
- Низкий RPS: кэш юрлиц 12–24 ч, цена лота 15 мин.
- Дисклеймер в UI: аналитика открытых сведений, не оферта купить.
- Не делать: автозаявку, автоставку и автоматическое решение капчи; при challenge допускается ручной CloakBrowser через CDP.
