# Дорожная карта до полноценного MVP

Актуально на 31 августа 2026 года. План опирается на текущий код, контрольный
прогон реальных источников и правило проекта: использовать API только при
подтверждённом бесплатном production-доступе; в остальных случаях — публичные
страницы и браузерный fallback через CloakBrowser.

## 1. Что считать полноценным MVP

MVP должен без ручного импорта находить лоты дебиторской задолженности минимум в
двух независимых публичных источниках, подтверждать актуальную цену и срок,
выделять дебитора, проверять основные стоп-факторы, рассчитывать объяснимый score
и отправлять только пригодные к проверке кандидаты в Telegram и web-интерфейс.

В MVP не требуется автоматическое юридическое заключение или гарантия взыскания.

Этап 3 добавляет наблюдаемый feedback-контур и договорной REST-переключатель
ЕФРСБ. REST отключён по умолчанию и не включается без явного подтверждения
договора; бесплатный публичный парсер остаётся независимым резервом.
Каждый факт должен иметь источник, время получения и состояние свежести. Если
реестр недоступен, система показывает typed gap, а не подставляет ноль и не
делает вид, что проверка завершилась.

## 2. Текущая подтверждённая база

Контрольный прогон текущей реализации дал следующий результат:

- основной seed — бесплатный публичный JSON ЦДТ;
- импортировано 244 текстово подтверждённых активных лота;
- все 244 лота получили score: 10 класса C и 234 класса D;
- в базе 129 дебиторов, у 23 есть свежая идентификация ФНС;
- на контрольном ИНН официальная PDF-выписка ЕГРЮЛ распознала недостоверные
  сведения и решение о предстоящем исключении, после чего сигнал был остановлен;
- API отдаёт список кандидатов и подробную карточку со стоп-факторами и gaps;
- регрессионная проверка: 163 backend-теста, 2 web-теста, Ruff и mypy прошли;
- Docker-приложение и PostgreSQL поднимаются и проходят health-check.

В этапе 1 добавлены событийное пробуждение зависимых score/alert worker-циклов,
счётчики changed/unchanged/rejected в `ImportRun`, endpoint
`/api/v1/workers/status` и диагностика фактического JSON-маршрута ЦДТ с proxy
признаком. Повторный живой импорт 244 карточек дал 244 `unchanged`, после чего
score и alerts завершились автоматически, а `stale_scored_lots` стал равен 0.

Это уже рабочее ядро, но пока не полноценный MVP: нужен второй источник лотов,
устойчивое обогащение, наблюдаемость и пользовательский суточный цикл.

Этап 2 реализован в текущей ветке: добавлены `trade_source_refs` для
универсального provenance (CDT больше не записывает новый URL в
`trades.efrsb_url`), `party_source_checks` со статусом каждой проверки ЕГРЮЛ,
ФССП и КАД, а юридические признаки переведены из ложного `false` по умолчанию
в `true/false/unknown`. Старые значения миграция переводит в `unknown`, чтобы
не выдавать непроверенные отрицательные факты. API и web показывают источники,
время проверки и «не проверено», а скоринг добавляет typed gaps
`kad_unverified`, `fssp_unverified` и `claim_evidence_unverified`.

## 3. Альтернативные способы получения данных

| Источник | Нужные данные | Бесплатный транспорт MVP | Резервный путь | Приоритет |
|---|---|---|---|---|
| ЦДТ | Лоты, цена, интервалы, документы | Публичный JSON списка и карточки | HTML/CloakBrowser, контроль схемы | P0 — уже работает |
| ГИС Торги | Дополнительные объявления и карточки | Публичные JSON, RSS и open-data файлы | CloakBrowser с российского маршрута | P1 |
| Альфалот | Лоты банкротства | HTML/JSON, который вызывает публичная карточка | CloakBrowser | P1 |
| Lot-online | Лоты, поиск по ИНН/ЕФРСБ/делу | Публичный каталог и карточки | CloakBrowser | P1 |
| МЭТС, uTender, Фабрикант | Цена, шаг, срок, документы | Бесплатный frontend JSON после проверки или HTML | CloakBrowser | P1/P2 |
| ЕФРСБ | Проверка сообщения и реквизитов торгов | Публичный HTML | CloakBrowser на российском маршруте | P2, не блокирует seed |
| ЕГРЮЛ/ЕГРИП | Идентичность и adverse-факторы | Бесплатный поиск по ИНН и официальная PDF-выписка | CloakBrowser | P0 — уже работает |
| «Прозрачный бизнес» | Статус, связи, адрес, массовый руководитель | Публичная карточка/запросы frontend | CloakBrowser | P2 |
| ГИР БО | Выручка, активы, отчётность | Публичная карточка конкретной организации и файлы | CloakBrowser | P2 |
| КАД | Дела, банкротство, судебный акт | Публичный поиск и карточка дела | CloakBrowser на российском маршруте; поиск по известному номеру дела | P2 |
| ФССП | Производства и безрезультатность взыскания | Публичный Банк данных | CloakBrowser с сохранённым профилем | P2 |
| TBankrot/Heveya | Обнаружение пропусков | Публичные страницы агрегатора | CloakBrowser | P3, только резерв |

Production REST ЕФРСБ, массовая выгрузка ФНС и API ГИР БО не входят в базовый
план: они требуют договора или оплаты. Внутренние endpoint публичного frontend
можно использовать только без обхода авторизации, с небольшим rate limit,
контролем схемы и запасным браузерным адаптером.

## 4. Очередь реализации

### P0. Зафиксировать надёжность текущего ядра — 1–2 рабочих дня

1. Расширить существующий `ImportRun` метриками по источнику и возрастом
   последнего успешного снимка; не создавать параллельную таблицу состояния.
2. Ввести единый per-domain rate limiter, bounded retry и circuit breaker.
3. Отключить подробный SQL log в production и добавить структурированные логи с
   `run_id`, `source`, `lot_id` и `error_kind`.
4. Проверить advisory lock планировщика, повторный запуск после падения и
   идемпотентность ingest/enrich/score/alert.
5. Добавить retention для сырых снимков и маскирование секретов в логах.

**Приёмка:** два последовательных запуска не создают дубликаты; отказ одного
источника не останавливает остальные; `/ready` не возвращает успех без БД;
секреты не появляются в логах и API.

### P1. Подключить второй и третий поток лотов — 3–5 рабочих дней

1. Реализовать общий интерфейс `LotSource` и адаптер ГИС Торги: RSS/поиск,
   open-data JSON, карточка, исходная ссылка и raw snapshot.
2. Проверить ГИС Торги с российского IP/CloakBrowser и закрепить fixture фактической
   схемы до написания parser contract.
3. Реализовать адаптеры Альфалот и Lot-online. Затем по той же схеме добавить
   первую доступную из МЭТС/uTender/Фабрикант.
4. Нормализовать внешний ключ лота и дедупликацию по сочетанию: идентификатор
   ЕФРСБ, ссылка ЭТП, номер торгов/лота, ИНН должника и хэш описания.
5. Добавить source-priority: цена и срок берутся с исходной ЭТП, агрегатор только
   сообщает о пропуске.

**Приёмка:** минимум два независимых seed-источника дают реальные лоты; повторный
импорт обновляет цену/срок без дублей; у каждой карточки есть `source_url`,
`fetched_at`, raw hash и явный статус актуальности.

### P2. Закрыть минимальный due diligence — 4–6 рабочих дней

1. Добавить кэш ЕГРЮЛ по ИНН и отдельное время проверки идентичности и статуса.
2. Через DevTools публичного сайта зафиксировать действующий протокол
   «Прозрачного бизнеса», реализовать parser contract и CloakBrowser fallback.
3. Реализовать публичный per-INN адаптер ГИР БО; сохранять период отчётности,
   выручку, активы и ссылку на исходный файл. Не использовать платную базовую
   выгрузку/API.
4. ✅ Базовый browser-first адаптер КАД реализован: запрос выполняется same-origin
   `POST /Kad/SearchInstances`, ответ проверяется по схеме, а HTTP `451` сохраняется
   как `route_blocked`. Следующий шаг — российский маршрут и карточки известных дел.
5. ✅ Форма ФССП реализована через headed CloakBrowser. CAPTCHA проходит оператор
   в сохранённом профиле; после таймаута результат кэшируется как typed `challenge`.
6. Хранить provenance отдельно для каждого поля и запрещать скорингу использовать
   просроченный или неподтверждённый факт.

**Приёмка:** не менее 70% дебиторов из кандидатов имеют подтверждённую ФНС
идентичность не старше 24 часов; каждый внешний факт имеет источник и дату;
недоступность КАД/ФССП отображается как gap и блокирует автоалерт по правилам
скоринга.

### P3. Извлечь юридические факты из документов — 3–5 рабочих дней

1. Скачивать договор цессии, решение суда, исполнительный лист и положение о
   торгах через доменный allowlist, лимит размера и проверку MIME.
2. Делать локальное извлечение текста из PDF; OCR включать только для сканов.
3. Выделять номер дела, сумму основного долга, проценты/неустойку, дату решения,
   наличие исполнительного листа, срок исковой давности и ограничения уступки.
4. LLM использовать только для извлечения в строгую схему с цитатой страницы;
   отсутствие цитаты означает `unknown`, а не подтверждённый факт.
5. Добавить ручной экран проверки спорных полей перед переводом в A/B.

**Приёмка:** минимум 90% скачанных документов имеют сохранённый hash и статус
обработки; критический факт в карточке ведёт к документу и странице; ошибка OCR
не превращается в отрицательный факт.

### P4. Сделать ежедневный пользовательский цикл — 2–3 рабочих дня

1. В Telegram отправлять краткий digest новых и изменившихся кандидатов, а не
   повторять один и тот же алерт.
2. Добавить действия `Открыть`, `Наблюдать`, `Отклонить`, `Ошибка данных` и
   сохранять feedback.
3. В web добавить фильтры по классу, EV, цене, сроку, источнику, полноте данных и
   стоп-факторам; показать свежесть и provenance рядом с полем.
4. Формировать карточку решения: цена сейчас, следующий шаг снижения, дедлайн,
   EV, max bid, стоп-факторы, gaps и ссылки на первоисточники.

**Приёмка:** новый кандидат появляется один раз; изменение цены создаёт отдельное
событие; пользователь может открыть первоисточник и объяснение score из одного
сообщения.

### P5. Развёртывание и эксплуатация — 2 рабочих дня

1. Разместить collector и CloakBrowser на локальном Windows-хосте или российском
   VPS; CDP оставлять только на loopback/закрытом туннеле.
2. Разнести API и scheduler роли настройкой, оставить один лидер scheduler.
3. Настроить PostgreSQL backup, health/readiness, алерт о падении источника и
   суточный отчёт покрытия.
4. Хранить Telegram/OpenAI/DB credentials только в secret store окружения.
5. Провести суточный canary с низкой частотой, затем контрольный прогон с
   сохранённым отчётом и десятью лучшими кандидатами.

**Приёмка:** сервис переживает рестарт; резервная копия восстанавливается;
источник с ошибкой виден в диагностике; контрольный прогон воспроизводим по
одной команде и не требует ручного редактирования БД.

## 5. Гейты выпуска MVP

Релиз можно назвать MVP только при одновременном выполнении условий:

- работают минимум два независимых источника лотов;
- не менее 90% импортированных лотов имеют исходную ссылку, снимок и актуальную
  цену/срок либо явный gap;
- не менее 60% подходящих по тексту лотов имеют извлечённый ИНН дебитора;
- не менее 70% дебиторов-кандидатов проверены ФНС за последние 24 часа;
- ни один лот со stop-фактором или просроченными обязательными данными не попадает
  в Telegram как рекомендация;
- score воспроизводим, а каждый множитель объясняется в API/UI;
- есть один успешный суточный canary и финальный контрольный прогон с top-10;
- unit/integration suite, Ruff, mypy, Docker smoke и миграции проходят в чистом
  окружении;
- секреты отсутствуют в Git, логах и API-ответах.

## 6. Что сознательно не делать до MVP

- не покупать API, пока бесплатные публичные пути дают достаточное покрытие;
- не включать недокументированный endpoint как единственный канал данных;
- не автоматизировать обход CAPTCHA: её проходит оператор в CloakBrowser;
- не считать отсутствие результата доказательством отсутствия долга/дела;
- не выдавать LLM-вывод без ссылки на документ за установленный факт;
- не калибровать «вероятность взыскания» без фактической истории исходов.

## 7. Рекомендуемый порядок ближайших задач

1. `source_runs`, метрики свежести, circuit breaker и production logging; базовые
   browser counters уже доступны в `/api/v1/diagnostics/sources`.
2. ГИС Торги на российском маршруте; при нестабильности — Альфалот как второй seed.
3. Lot-online и единая межисточниковая дедупликация.
4. «Прозрачный бизнес» и ГИР БО по ИНН.
5. KАД и ФССП через CloakBrowser с кэшем и typed gaps (базовый транспорт готов).
6. Provenance документов и юридических фактов.
7. Telegram digest/feedback, web-фильтры и суточный canary.

Оценка до релизного MVP: 15–23 рабочих дня одного разработчика при стабильном
доступе к российским публичным сервисам. Сетевые блокировки не должны сдвигать
весь релиз: каждый источник подключается независимо, а его недоступность явно
видна в диагностике и score gaps.
